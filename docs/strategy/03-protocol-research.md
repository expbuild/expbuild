# expbuild Multi-Protocol Cache: Protocol Research and Integration Boundaries

Research date: 2026-09-28. Positioning premise: prioritize enterprise self-hosting while leaving room for SaaS. This document verifies only official documentation, specifications, source code, and release notes; **no protocol interoperability PoC was run against expbuild**. “Verified” means only that a clear source exists, not that the current implementation is compatible. main/latest/current documentation changes; pin client versions, specification commits, and test results before release.

## Conclusions

The platform is well suited to unifying identity, namespaces, storage, quotas, lifecycle, operations, and observability. Each tool remains responsible for cache-key calculation and artifact formats. Do not promise cross-tool cache hits among Bazel, Gradle, sccache, Nx, and Turborepo. Deduplicating bytes that happen to be identical is a physical storage optimization, not reuse of semantics across tools.

Considering the repository audit and platform-development cost, the final initial-release commitment covers just two ecosystems: **stabilizing existing REAPI cache capabilities + Gradle HTTP**. sccache WebDAV belongs in P1.x; if seed customers primarily use Rust/C++, replace Gradle with it rather than expanding the first release. Bazel HTTP is a new protocol surface, placed in P1.x with separate acceptance criteria; it cannot be called an existing capability. Turborepo, Nx, and ccache belong in P1.x; BuildKit registry and Maven in P2; remote execution and Nix / GitHub Actions protocol emulation are P3 decisions driven by demand. P0 is a controlled enterprise pilot; P1 is the enterprise general release.

See the [overall plan](README.md) and [roadmap](06-roadmap-and-validation.md) for final phase scope. P0 means completing management, security, and operational workflows for two ecosystems in a controlled pilot, not maximizing protocol count.

## Additional Ecosystems: Protocol Reuse and Client Extensions

- **Pants / Buck2**: prioritize these as additional REAPI client compatibility profiles rather than creating another platform protocol. Pants officially provides REAPI remote caching; Buck2 can connect to REAPI services, but cache policies, deferred materialization, platform properties, and retention assumptions still need separate tests. Bazel passing does not automatically mean either passes. Include them as P1.x/P2 customer-demand candidates without blocking the initial release. [Pants stable docs](https://www.pantsbuild.org/stable/docs/using-pants/remote-caching-and-execution/remote-caching), [Buck2 RE](https://buck2.build/docs/users/remote_execution/), [deferred materialization](https://buck2.build/docs/users/advanced/deferred_materialization/).
- **Go GOCACHEPROG**: Go 1.24 moved the external cache-process mechanism out from behind an experimental flag; it takes over build/test caching through a subprocess JSON protocol. Integration therefore needs a local helper bridging to expbuild, not an HTTP URL assigned directly to the variable. Treat it as a future demand candidate (P3 by default, potentially replacing other items for explicit customer needs); validate toolchain versions, helper distribution, the process protocol, result-file materialization, concurrency, and exit behavior. It differs from GOPROXY's module dependency download proxy, which is a separate product surface. [Go 1.24 GOCACHEPROG](https://go.dev/doc/go1.24#GOCACHEPROG), [official protocol types](https://go.dev/src/cmd/go/internal/cacheprog/cacheprog.go).

## Direct Requirements for the Shared Core (Design Inferences)

1. **Separate logical cache keys from content digests.** Suggested logical-key components are tenant / namespace / protocol / entry-kind / client-key; compute a separate storage digest for content bytes. Explicitly record digest algorithm and encoding. Do not assume a hash in a path is the hash of the uploaded body.
2. **At least three entry models.** Opaque single archives (Gradle, Turbo, Nx, sccache, etc.); index→content graphs (Bazel AC/CAS, Maven build info); manifest/tag/closure graphs (OCI, Nix). Reuse common storage capabilities; adapters own reference extraction, commit atomicity, cleanup roots, and protocol error mapping.
3. **Stage writes.** Temporary upload→integrity verification→content visibility→index commit; data left by cancellation, timeouts, or crashes must be reclaimable. Do not first return an AC/manifest hit and then discover that dependent blobs are not durable. Provide atomic create-if-absent for protocols requiring immutability and concurrency control for updatable indexes; do not impose platform-wide last-write-wins.
4. **GC requires references and read protection.** Delay cleanup of unreferenced blobs after index/manifest expiry; protect active uploads, recent reads, and objects required by builds. After returning a successful Bazel AC response, protect its outputs during the download window. Single entries can use TTL/LRU, but sharing an “oldest file first” deletion policy with reference-graph entries is unsafe. Management features include GC dry-run, estimated reclamation, deletion audit, and quarantine.
5. **Separate authentication, byte integrity, and provenance trust.** A token says who may call, a digest says whether bytes match, and a signature identifies bytes authorized by a key; none automatically proves they were built from the intended source and toolchain. The server must at least separate trusted CI, developer, and PR/untrusted write domains. Allow consumption from trusted upstreams, but do not let PR first writes claim production keys. Trusted artifact promotion requires build identity and policy.
6. **Derive tenant ownership from server-side identity.** instance_name, teamId, URL paths, and S3 prefixes only locate candidate resources; arbitrary client declarations cannot grant access. Cross-tenant physical deduplication is disabled by default; enabling it later requires addressing existence side channels, encryption boundaries, and quota accounting.
7. **Compression must not break protocols.** Transport compression, client archive compression, and internal server compression are separate layers. Initially preserve compressed/signed content as opaque byte streams; Bazel handles plaintext digests according to REAPI compression semantics, and OCI preserves the specified manifest/layer representations. Avoid global HTTP gzip middleware that changes signatures, lengths, or Range behavior.
8. **Plugin protocols must expose capabilities beyond get/put.** Suggested interfaces include authorize-context, lookup/read/write, begin/commit/abort upload, extract-references, validate, error mapping, capability declaration, retention roots, and telemetry. The core owns rate limits/quotas/storage transactions; adapters cannot access other tenants arbitrarily. P0 starts with compile-time modules; P1/P2 develops isolated process plugins to avoid paying too much for a hot-plug ABI in the initial release.
9. **Common metrics must avoid false precision.** HTTP 200, blob GET, HEAD success, and AC hit do not equal “one entire build saved.” The platform uniformly reports request/entry/byte hit rates, bandwidth, capacity, and latency; saved build time needs client build events and a comparison baseline. Client fields such as Turbo duration must identify their source and must not be mixed with measured CPU seconds.

## Easily Misunderstood Boundaries

- Bazel REAPI cache compatibility does not imply support for Execute, workers, schedulers, sandboxes, or toolchains; plan remote execution separately.
- sccache distributed compilation likewise uses a separate scheduler/build server and is not automatically provided by WebDAV/S3 storage support. [sccache distributed quickstart](https://github.com/mozilla/sccache/blob/main/docs/DistributedQuickstart.md)
- Gradle task-output cache is neither configuration cache nor a Maven/Gradle dependency proxy. A cache service also cannot fix client build-definition issues such as undeclared inputs or nondeterministic tasks. [Gradle build cache](https://docs.gradle.org/current/userguide/build_cache.html)
- BuildKit registry cache is the preferred available route. Current Docker docs mark S3/azblob backends as unreleased, while the main BuildKit repository marks them experimental. These are not conflicting guarantees of stability: pin and test Docker/Buildx distribution channels, drivers, and standalone BuildKit separately; do not broadly claim Docker S3 cache is fully available. [Docker backends](https://docs.docker.com/build/cache/backends/), [BuildKit README](https://github.com/moby/buildkit)
- Using expbuild's Gradle/Turbo/Bazel cache within GitHub Actions is ordinary CI integration; implementing GitHub Actions cache-service compatibility is separate, maintenance-intensive protocol work. BuildKit's gha exporter has explicit `url_v2/token` parameters, but that does not establish identical replacement configuration for stock actions/cache. [Docker gha backend](https://docs.docker.com/build/cache/backends/gha/)
- Do not classify current Nx self-hosted servers as requiring a Powerpack purchase: the official 2025-03 announcement introduced a free open-specification route, and the 2025-12 update says Powerpack is no longer a standalone product; the current self-hosting specification is available. Assess Nx Cloud/Enterprise feature licensing separately. [Official Nx announcement](https://nx.dev/blog/custom-runners-and-self-hosted-caching), [Powerpack update](https://nx.dev/blog/introducing-nx-powerpack)

Each compatibility profile includes at least `client_version`, `client_binary_digest`, `spec_commit`, `server_version`, OS/CPU/runtime, key flags, authentication method, compression method, fixtures, test date, result links, and known limitations. The product UI should display “certified/experimental/unverified/deprecated” rather than an unscoped support checkmark.

## Suggested P0/P1 Protocol PoC Acceptance Criteria

These implementation acceptance checks have not yet been performed:

1. A real client writes during a cold build; another clean machine reads during a warm build; outputs match an uncached build. Cover expected misses caused by changes to source, compiler/JDK, environment parameters, and dependencies.
2. Writes with read-only credentials actually fail; identical keys across tenants/projects/protocols cannot be read without authorization; untrusted PRs cannot contaminate trusted domains; effective client behavior after credential revocation matches the contract.
3. Small files, zero-length blobs, large files, concurrent duplicate writes, interrupted-stream retries, duplicate commits, full disks, object-store failures, database failures, and concurrent GC; return protocol-expected errors instead of generic JSON 500 responses.
4. Bazel-specific coverage includes directory/tree, stdout/stderr, missing CAS, ByteStream offset/resume, mixed batch results, uncompressed and zstd digests, and the AC reference download window.
5. Gradle coverage includes 404, 413, Expect-Continue, and redirects; sccache covers webdav features, actual HTTP methods/paths, Basic/Bearer, different toolchain keys, and compressed content. Successful curl requests alone are insufficient.
6. P1 Turbo coverage includes signatures enabled/disabled/invalid, headers, team scope, and events; Nx covers concurrent first writes, 409, and actual archive formats; ccache covers both helpers and legacy HTTP.
7. Establish customer-workload performance baselines first: entry hit rate, byte hit rate, P50/P95/P99 lookup latency, upload/download throughput, cold→warm build wall-clock time, and CPU/disk/memory/bandwidth costs. Do not assume a universal “10× speedup” target.

## Commercial and Licensing Boundaries

This section describes product-engineering boundaries, not legal advice. Implementing public interfaces, distributing open-source clients, embedding third-party servers, and reselling a vendor's hosted service are different decisions. Register each dependency's pinned-version LICENSE/NOTICE, trademark terms, and commercial terms.

- The Nx open self-hosting specification and Nx Cloud/Enterprise have different product licenses. Do not copy closed-source SDKs/control planes or infer distribution rights from the open API. The existing official API route adequately covers expbuild's basic remote cache.
- Gradle's native HTTP client can connect to an independent implementation. Separately check product terms when using Gradle's cache-node image or Develocity integration; the open-source Gradle client license is not the license for every server product. [Official Gradle documentation](https://docs.gradle.org/current/userguide/build_cache.html)
- Turborepo / Nx repositories have their own open-source license files, while hosted services have separate terms. Prioritize public-protocol implementation under an independent expbuild brand. [Turbo LICENSE](https://github.com/vercel/turborepo/blob/main/LICENSE), [Nx LICENSE](https://github.com/nrwl/nx/blob/master/LICENSE)
- ccache as a whole uses GPL-3.0-or-later. If expbuild packages bundle or modify clients/helpers, review distribution obligations per project and version. HTTP interoperability alone does not mean the server and client necessarily share the same license. [ccache license](https://ccache.dev/license.html)
- The open actions/cache client does not constitute a GitHub guarantee of long-term stability for the complete third-party server protocol. An expbuild-owned Action/CLI has clearer maintenance responsibilities. Any later decision to provide transparent compatibility must accept upstream-upgrade regression costs; a public SDK does not imply official certification.
