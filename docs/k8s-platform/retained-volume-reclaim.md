# Retained-volume reclaim

After an instance is deleted and its PVC retained under `Retain`, a project administrator can select “Restore instance using retained volume” in instance details. The form keeps the original template version and requires new runtime resources, cache budget, and deletion policy; the volume, namespace, and storage class do not change. `GET /v1/projects/{projectId}/instances/{instanceId}/retained-volume` returns the PVC UID, requested capacity, and allocated capacity. When submitting `POST /v1/projects/{projectId}/instances/{instanceId}/retained-volume/reclaim`, use that PVC UID as `If-Match`, together with a new `Idempotency-Key` and the complete instance configuration. The new password is returned only in the initial acceptance response.

The management API checks project permissions, the old instance binding, template version, the PVC's project/instance/old CR UID labels, storage class, Bound state, and minimum capacity. Within a project transaction, it rechecks the binding and reserves instance count, CPU, memory, and storage. Failed validation neither queues an operation nor releases existing storage reservations. The worker creates a new CR and separate credentials using the same instance ID. The CR's `storage.reclaim` fixes the old CR UID and PVC UID, and Kubernetes admission rejects subsequent changes. If the create response is lost, the worker adopts an existing CR only when its operation ID, request hash, and complete configuration match.

Initially, the Operator reports only `VolumeReclaimPending`; it does not transfer PVC ownership or create workloads. Only after persisting the new CR UID in the binding does the worker write the `reclaim-bound-uid` annotation to the CR. The Operator then rechecks the PVC UID, original ownership, project/instance labels, storage class, access modes, requested and allocated capacity, deletion state, ownerReference, and all Pod references, and uses resourceVersion optimistic locking to transfer the PVC's instance UID label. Retries recognize the same new UID and reject replacement volumes with the same name or mismatched transfers. Once the new instance is ready, old credentials are cleaned up and the binding returns to active; if Retain deletion is selected again, the new CR UID becomes the owner of the next retained volume.

Failed operations retain resource reservations. A failure with an existing new CR can resume checks through the operation retry endpoint without recreating the CR or reissuing a password that has already been cleared. If the CR does not exist and the PVC still belongs to the original UID, a new reclaim request can be submitted after verifying the volume. If the transferred CR is deleted externally, resource reconciliation reports an anomaly requiring manual intervention. The platform does not promise cross-node fencing for arbitrary CSI drivers, erasure of underlying PV data, or migration between engines. Read/write retention acceptance checks on real kind clusters are included in the isolated-cluster script; consult the corresponding CI results for outcomes.
