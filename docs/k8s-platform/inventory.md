# Resource reconciliation

Project members can view the latest inventory in the “Resource reconciliation” panel and request a new scan. The background process scans CacheInstances and PVCs by project and reports differences between records and actual resources; it does not adopt or delete resources, or rewrite instance lifecycles, credentials, or quota reservations.

Current coverage includes instance UID/ownership conflicts, missing instances, differences between submitted configuration and CR spec, unexpected deletion, deleted instances reappearing, abnormal PVC ownership/state, missing retained volumes, volumes remaining after deletion, and unregistered CRs/PVCs in the project namespace. Judgment is deferred for instances with operations in progress, which appear as InProgress. Healthy means only that this scan found none of these resource discrepancies; it does not prove cache requests, monitoring, or all Kubernetes child resources are healthy.

`GET /v1/projects/{projectId}/inventory` returns result and checkedAt; both may be null before the first scan. Results distinguish Healthy, Drift, InProgress, and Unavailable, and include issue details, total issue count, and resource counts. Errors or permission failures do not produce an empty healthy inventory. The UI shows the last check time and marks results stale after five minutes.

`POST /v1/projects/{projectId}/inventory/refresh` requires project membership and the existing Origin/CSRF protection, and returns 202/scheduled. Requests are coalesced, with at least ten seconds between scans; a scan already in progress can satisfy the request. The UI reads results every ten seconds. Regular background scans run every sixty seconds; if platform state changes during a scan, it retries after five seconds.

Background workers divide work using three-minute database leases and do not hold project row locks during network reads. Before publishing, a worker verifies that it still owns the lease and compares the fingerprints of instance bindings and operation records again. Late results from a worker whose lease has been taken over cannot overwrite newer observations, and operations submitted during a scan are not reported as confirmed discrepancies. The cluster namespace's UID/ownership is checked before and after list reads; a failed scan releases no resource quota.

To bound resource consumption per scan, the database scan covers at most 1000 instance bindings; CRs and PVCs each have a limit of five pages with 200 entries per page. Incomplete pagination or exceeded limits return Unavailable rather than treating truncated results as complete. At most 200 issue details are displayed, alongside the full issue count and a truncated flag. Sharded scans and historical archiving for larger projects still need expansion.

Local tests cover identity, ownership, configuration drift, missing retained volumes, orphan resources, pagination limits, namespace replacement, database leases, skipping across replicas, late results, concurrent operations, and read-only permissions. Real Helm/API tests include injecting an unregistered PVC, observing drift, verifying no automatic deletion, and recovery after manual removal. These passed the [full isolated-cluster CI](https://github.com/expbuild/expbuild/actions/runs/36679678906) at commit 3872cfe, covering internal, Gateway, and Cilium modes.

Explicit remediation workflows for other discrepancies, inventory of additional resources such as Pods/Secrets/routes, and retained-volume reclaim remain follow-up work. The current scan does not replace these capabilities.

Reconciliation also checks that the independently stored template name/version matches the actual CR; missing binding versions are reported as unknown. Resource reservation checks compare the CR's storage requirements, CPU/memory requests and limits, and the requested and actual capacity of the owned PVC. Actual configuration exceeding recorded reservations, unknown reservations, or unparseable quantities are all reported as discrepancies. Paused instances are still checked for the reservations required to resume; detached instances are checked only for storage. Historical reservations above current configuration are neither automatically released nor reported as insufficient. Quantities are compared using exact integer ratios; fractional CPU, binary capacities, and exponent notation do not depend on floating-point rounding. Template and reservation fields are included in the scan fingerprint; changes during a scan withdraw definite conclusions and trigger another scan. Automatic scanning only reports discrepancies: it does not adjust accounting or equate storage capacity with actual file usage.

Platform administrators can now call `POST /v1/projects/{projectId}/instances/{instanceId}/reservations/reconcile` for a single stable instance. The UI shows this action only in fresh, untruncated reconciliation results with no other anomalies for that instance. The request rescans the project namespace, checks the CR/PVC project labels, instance UID, template, and configuration, then rechecks binding and operation fingerprints under the project row lock. Only active or detached instances are eligible; operations in progress, missing resources, ownership conflicts, and quantities that are unknown or cannot be safely represented are rejected. Storage uses the maximum of the CR requirement, PVC request, and actual allocated capacity; CPU/memory for running instances use the maximum of requests and limits, rounded up to the accounting units. The database only raises historical reservations: it does not reduce reservations or modify Kubernetes resources. Detached instances receive storage corrections only. Actual usage is recorded even if it already exceeds project limits; subsequent creation or expansion will be rejected by existing quota admission. Every reconciliation records an audit event and schedules another scan. Kubernetes and the database have no cross-system atomic snapshot, so external expansion after a scan still requires detection by later reconciliation; this is neither automatic adoption nor a general remediation workflow.
