# Gradle HTTP build-cache engine (in development)

Status updated: 2026-10-08. New instances use `gradle-http@0.2.0`; `0.1.0` remains a historical version. Native Gradle and selected disposable-cluster paths pass; production storage and scale remain unqualified. See the [support matrix](support-matrix.md) and [current CI results](progress.md#current-validation).

Gradle's official HTTP build cache reads opaque task-output archives with GET and uploads them with PUT; HTTP Basic is its native authentication method. See [Gradle Build Cache](https://docs.gradle.org/current/userguide/build_cache.html) and the [HttpBuildCache API](https://docs.gradle.org/current/dsl/org.gradle.caching.http.HttpBuildCache.html) for the protocol. This endpoint differs from Bazel HTTP CAS/AC; Gradle archives cannot be validated as Bazel digests.

`operator/internal/gradlecache` provides a separate data plane: `GET/PUT /cache/<32- or 64-character lowercase hexadecimal key>`, bcrypt htpasswd authentication with two identities (client and health probe), per-entry size limits, an instance-wide budget, cleanup by last access time, and first-write-wins behavior for the same key. Uploads first write to a temporary file on the same volume and, after synchronization completes, publish atomically using a hard link. Restart scans rebuild the index from the persistent directory and remove leftover temporary uploads. Reads return 200 for hits and 404 for misses; uploads return 201 for success, 409 for duplicate keys, and 413 for oversized entries. Other methods are rejected. The authenticated `/status` endpoint returns entry count, usage, budget, and GET hit/miss and PUT success/rejection counters for the current process. In the current engine, `health` can read `/status` and `/metrics` but cannot access cache entries; the client can read/write entries and read status, but cannot scrape metrics. The credentials file permits at most two distinct records; malformed content causes the entire file to be rejected.

The `gradle-http@0.2.0` template is compiled into the Operator registry and CRD; historical `0.1.0` instances retain their original capability declaration and image binding. Installation must configure a trusted `images.gradle` SHA256 image before the management API permits creation; existing instances remain manageable. Each instance uses a single-replica StatefulSet, separate PVC, separate Secret, and Service. After the workload revision is ready, the Operator reads authenticated `/status` and confirms the capacity budget before reporting Ready/PolicyApplied. Gateway HTTPS connection endpoints retain the `/cache/` path. The management API/UI provides capacity, entry, and request counts; `0.2.0` adds continuous native hit/miss, latency, traffic and eviction metrics through the [observability integration](observability.md). The generated Kotlin initialization script enables CI uploads and defaults to reads on development machines. That client setting does not restrict the credential's server-side write authority. The template and UI have passed PostgreSQL, real-browser, Kubernetes API server admission, and Helm rendering tests within the [documented test boundaries](testing.md).

Local validation with official Gradle 8.14.3 (SHA256 verified) covered the first upload, a `FROM-CACHE` hit using a second fresh project and Gradle user directory, and re-execution with caching disabled. The test client's Kotlin initialization script follows the same structure as the console instructions. This validation is included in platform CI. Disposable kind clusters also verified reads/writes through PVC/Service, persistence across Pod recreation, pause/resume, credential rotation, and Retain/Delete behavior. Helm/API internal mode verified creation, statistics, rotation, and deletion; Gateway mode verified `/cache/` HTTPS access and route revocation. Supported storage must provide atomic hard links within one filesystem; production CSI, remounting across nodes, real DNS, and high-load performance require separate qualification. The overhead of bcrypt verification, access-time updates, and restart index scans also needs measurement under real workloads.
