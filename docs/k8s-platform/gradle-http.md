# Gradle HTTP build-cache engine (in development)

Gradle's official HTTP build cache reads opaque task-output archives with GET and uploads them with PUT; HTTP Basic is its native authentication method. See [Gradle Build Cache](https://docs.gradle.org/current/userguide/build_cache.html) and the [HttpBuildCache API](https://docs.gradle.org/current/dsl/org.gradle.caching.http.HttpBuildCache.html) for the protocol. This endpoint differs from Bazel HTTP CAS/AC; Gradle archives cannot be validated as Bazel digests.

`operator/internal/gradlecache` provides a separate data plane: `GET/PUT /cache/<32- or 64-character lowercase hexadecimal key>`, bcrypt htpasswd authentication with two identities (client and health probe), per-entry size limits, an instance-wide budget, cleanup by last access time, and first-write-wins behavior for the same key. Uploads first write to a temporary file on the same volume and, after synchronization completes, publish atomically using a hard link. Restart scans rebuild the index from the persistent directory and remove leftover temporary uploads. Reads return 200 for hits and 404 for misses; uploads return 201 for success, 409 for duplicate keys, and 413 for oversized entries. Other methods are rejected. The authenticated `/status` endpoint returns entry count, usage, budget, and GET hit/miss and PUT success/rejection counters for the current process. The `health` probe identity can access only `/status`; the client identity can read and write cache entries. The credentials file permits at most two distinct records; malformed content causes the entire file to be rejected.

The `gradle-http@0.1.0` template is compiled into the Operator registry and CRD. Installation must configure a trusted `images.gradle` SHA256 image before the management API permits creation; existing instances remain manageable. Each instance uses a single-replica StatefulSet, separate PVC, separate Secret, and Service. After the workload revision is ready, the Operator reads authenticated `/status` and confirms the capacity budget before reporting Ready/PolicyApplied. Gateway HTTPS connection endpoints retain the `/cache/` path. The management API/UI provides capacity, entry, and request counts and generates a Gradle Kotlin initialization script; CI users can upload, while development machines default to read-only access. The template and UI have passed local PostgreSQL, real-browser, Kubernetes API server admission, and Helm rendering tests.

Local validation with official Gradle 8.14.3 (SHA256 verified) covered the first upload, a `FROM-CACHE` hit using a second fresh project and Gradle user directory, and re-execution with caching disabled. The test client's Kotlin initialization script follows the same structure as the console instructions. This validation is included in platform CI. Disposable kind clusters also verified reads/writes through PVC/Service, persistence across Pod recreation, pause/resume, credential rotation, and Retain/Delete behavior. Helm/API internal mode verified creation, statistics, rotation, and deletion; Gateway mode verified `/cache/` HTTPS access and route revocation. Supported storage must provide atomic hard links within one filesystem; production CSI, remounting across nodes, real DNS, and high-load performance require separate qualification. The overhead of bcrypt verification, access-time updates, and restart index scans also needs measurement under real workloads.
