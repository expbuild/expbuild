# Project resource quotas

Platform administrators can select “View project quota” on the project page to configure limits for instance count, storage GiB, CPU millicores, and memory MiB. Project members can view quotas; ordinary project administrators cannot raise their own quotas. An empty value means unlimited, while 0 prohibits consumption. Existing projects default to unlimited. The API uses an independent quota revision and If-Match to avoid overwriting another administrator's changes, and records adjustments in the audit log.

`GET /v1/projects/{projectId}/quota` returns limits, reserved, unknownReservations, and revision, plus synchronization state. `PUT` accepts four fields of the same names: instances, storageGiB, cpuMillis, and memoryMiB, each an integer or null. The UI fetches them on demand and can refresh reservations after an operation completes. These are configuration reservations, not sampled CPU/memory usage or physical storage consumption.

## Accounting and release boundaries

- Instance creation and configuration updates reserve quota in the same PostgreSQL transaction that queues the operation; a project row lock serializes concurrent acceptance. Insufficient quota returns 409 and rolls back the entire transaction; idempotent replay does not reserve twice.
- Updates temporarily reserve the greater of the old and target values. CPU and memory reductions are settled only after success and confirmation that the current configuration has taken effect; storage does not shrink. Paused instances retain all reservations so their configuration can be honored on resume.
- Failed creates or updates may already have produced resources and continue to hold reservations. Accepting a deletion request does not release quota; after the worker confirms deletion is complete, Delete releases everything, while Retain releases instance count, CPU, and memory but retains storage. Storage is released after retained-volume cleanup completes.
- Limits cannot be set below current reservations. Failed operations and retained volumes may block new creation; recover or finish cleanup first.
- During upgrades, reservations are backfilled using the maximum configured values in historical operations, including failures, to avoid underestimating partially successful expansion. Non-deleted records that cannot be backfilled count toward unknownReservations; limits cannot be enabled in that state, and unknown values cannot be treated as zero. Existing successful updates can settle identifiable resources; anomalous historical records still require resource reconciliation.

## Kubernetes hard limits

The background process continuously maps the four limit types to the `expbuild-resources` ResourceQuota in the project namespace: instance count maps to `count/cacheinstances.cache.expbuild.io`, storage to `requests.storage`, and CPU/memory constrain both requests and limits. See the [official ResourceQuota documentation](https://kubernetes.io/docs/concepts/policy/resource-quotas/) for Kubernetes admission restrictions on excess resources. These are still configured quotas, not actual disk writes; tightening limits does not evict existing workloads.

Resource ownership, UID/resourceVersion, the absence of scope restrictions, and monotonic versions are checked; external objects with the same name or incompatible scopes are not adopted. Quantities are compared by their Kubernetes-equivalent values, so `1000m` and `1` do not cause repeated updates. When all limits are removed, only a quota confirmed to belong to the project is deleted, and its absence is subsequently confirmed.

The background process synchronizes under a project row lock, with SKIP LOCKED distributing work across replicas. It checks again about 30 seconds after success and retries incomplete or failed synchronization about every 2 seconds; each Kubernetes request has a timeout. Instance creation, modification, and rotation recheck the current quota before execution; if it is not ready, the asynchronous operation remains waiting. Deletion and retained-volume cleanup bypass this gate. Persistent failures remain subject to the operation's overall deadline; after repair, the existing retry mechanism can be used.

The API and UI distinguish saved quotas from cluster synchronization. The current revision is reported as Applied only when ResourceQuota spec and status.hard match and all count entries have been initialized; failure withdraws the observed version and returns a safe error code. Applied is the latest observation, timestamped by checkedAt, not a guarantee against future external changes. The project row lock spans Kubernetes requests with timeouts, so submissions for the same project may wait; performance at scale still requires load testing.

Direct Pod creation must also specify resource requests/limits subject to quota. Additional sidecars, RuntimeClass overhead, and other workloads in the project all affect actual cluster usage. Database reservations record only platform instances and do not automatically convert these external consumers into platform reservations. Actual Kubernetes admission still rejects excess usage, but operations may wait or fail, requiring subsequent resource reconciliation. Project members other than platform administrators should continue to operate only through the management API.

## Validation boundaries

Isolated PostgreSQL database tests cover concurrent acceptance, idempotency, version conflicts, all four dimensions, retained volumes, historical backfill, multi-replica synchronization, error recovery, and deletion bypassing the synchronization gate. The actual Kubernetes SDK is tested against a local HTTP service for request sequences, quantity normalization, ownership rejection, and versioned deletion; these are not real quota-admission tests.

The isolated Helm/API scenario now includes real ResourceQuota synchronization and server dry-run attempts to create an over-quota CR, PVC, CPU Pod, and memory Pod directly, requiring Kubernetes to return exceeded quota. CI results are pending. Hard quotas at production scale, external changes by cluster administrators, additional workloads, and resource reconciliation still require further validation.

Quota accounting for a newly added CRD may initially contain used values for built-in resources but lack the CR count entry. The platform remains Pending and does not treat missing values as zero. Tests pinned to Kubernetes 1.32 allow seven minutes for initial count initialization, covering [that version's default five-minute quota resynchronization period](https://github.com/kubernetes/kubernetes/blob/v1.32.0/pkg/controller/resourcequota/config/v1alpha1/defaults.go). Every Kubernetes request still has its own timeout, and resource operations remain subject to the overall deadline.
