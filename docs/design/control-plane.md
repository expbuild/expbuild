# Control Plane: Identity, Authorization, Management APIs, and Revocation Contract

Date: 2026-09-28. Status: **P0 development design awaiting implementation**, not a description of existing capabilities. The [master plan](../strategy/README.md), [management capabilities](../strategy/01-product-and-management.md), [architecture](../strategy/02-architecture-and-extension.md), and [roadmap](../strategy/06-roadmap-and-validation.md) provide the governing constraints; see the other designs in this directory for the data model and write consistency.

## 1. Delivery Boundaries and Gaps in the Current Implementation

P0 retains the TypeScript management service and React and uses PostgreSQL. The management service handles IAM, projects, policies, audits, and asynchronous management tasks; the Rust data plane handles artifact transfer, cache indexing, and quota enforcement. The two services use different database roles; browsers cannot directly access internal policy interfaces. P0 excludes public registration, billing, arbitrary ABAC, CI OIDC federation, and cross-tenant sharing. Enterprise OIDC belongs to P1; if it is a hard pilot requirement, it must replace other scope.

The current [Prisma schema](https://github.com/expbuild/expbuild-admin/blob/853a48c521100b89e287f2e98f2f1931f67be495/server/prisma/schema.prisma) has only `User.role`, `Project.ownerId`, and plaintext `Project.apiKey`, with no tenants, memberships, namespaces, or credential scopes. The [pipeline route](https://github.com/expbuild/expbuild-admin/blob/853a48c521100b89e287f2e98f2f1931f67be495/server/src/routes/pipeline.ts) overwrites the authorized project set with the client-supplied `projectId`. This design must replace these boundaries, not merely add menus to the old model; old keys are not reused as new credentials.

A self-hosted installation creates its first user, tenant, and administrator binding through a one-time local bootstrap command, then disables bootstrap. Subsequent users register through one-time join links generated by administrators; email delivery is not required. Platform administrators manage the installation and backend configuration; access to tenant artifacts requires separate tenant authorization.

## 2. Minimal Domain Model

All IDs are immutable UUIDs. Names and slugs are for display and lookup only; they are not authorization evidence, object keys, or native-tool routes. The “organization” displayed in the browser is a Tenant.

| Object | Required fields and constraints |
|---|---|
| Tenant | `id,name,status,authz_epoch,revision`; `active/suspended/deleting` |
| User / Session | Global user identity; sessions retain user, expiration, and revocation times; tenant permissions are not packed into a user's global `role` |
| TenantMembership | `tenant_id,user_id,role,status`; tenant roles `admin/member`; every tenant must retain at least one active admin |
| Principal | `tenant_id,id,kind,status,user_id?`; kind is `user/service_account`; the same global User maps to a different Principal in each tenant |
| Team / TeamMember | Flat teams within a tenant; members must have active membership in that tenant; no nested teams |
| Project | `id,tenant_id,name,description,status,revision`; tenant ownership replaces the single owner field |
| ProjectBinding | `tenant_id,project_id,subject_type,subject_id,role`; binds a person or team to `maintainer/developer/observer` |
| Namespace | `id,tenant_id,project_id,name,protocol_id,trust_domain,status,current_policy_version`; P0 protocols are `reapi/gradle`, trust domains are `trusted-ci/internal-dev/isolated-pr` |
| ServiceAccount | Tenant and project ownership, name, status, creator; no password, browser session, or organization-management privileges |
| Credential | `id,tenant_id,principal_id,verifier,pepper_version,expires_at,revoked_at,created_by,rotated_from_id,last_used_at`; associated with an immutable authorization scope |
| NamespaceGrant | `subject_type=principal/team`, principal/team ID in the same tenant, namespace, and actions; expand team membership before intersecting with credential scope |
| PolicyVersion | `tenant_id,version,authz_epoch,document,created_at`; immutable; namespace points to the current version; API revision controls concurrency |
| Audit / Outbox | Before/after summaries, actor, resource, `request_id,policy_version,occurred_at`; written in the same transaction as the business change |

`protocol_id/trust_domain` cannot change after namespace creation. Changing protocol or trust level requires a new namespace, new grants, and another warm-up; PATCH cannot elevate the trust level of existing content. P0 disallows implicit read fallback across namespaces. Cross-project sharing first requires a separate design for explicitly authorized references.

All child tables include `tenant_id` and bind to parents through composite foreign keys `(tenant_id,parent_id)`; namespaces additionally constrain their project ownership. Globally unique UUIDs do not replace tenant predicates. Teams and roles are used only to compute authorization; credentials ultimately expand to a concrete set of namespaces. P0 accepts neither `*` nor wildcards for future projects.

Alignment with the [metadata model](metadata-model.md): `Principal/Credential` are the minimal authoritative parent records referenced by the data plane; `User/Membership/Team/Binding/verifier` are control-plane supplementary tables/columns. The SQL draft does not claim to cover a complete IAM schema. A namespace is P0's unit of physical isolation and deduplication; physical domains are not merged merely because they share a tenant or trust level.

## 3. Permission Decisions and Preventing Filter Overrides

Management permissions and data permissions are separate. `tenant.admin` can manage members, projects, and policies within its tenant; `project.maintainer` can manage namespaces, service accounts, retention, and credentials within its project. Neither automatically receives artifact-read access. A `developer` can view authorized projects and request their own read-only credentials; an `observer` can only read metrics and metadata. Actual artifact reads require namespace `cache.read`; browser artifact exports additionally require `artifact.download`. `cache.invalidate` is a fixed permission of the two management roles within their respective scopes; observers and CI do not have it by default.

Internal actions retain `blob.write` and `result.publish`; the UI's “read/write” combination is `cache.read+blob.write+result.publish`. REAPI CAS uploads require only `blob.write`; AC updates additionally require `result.publish`. Gradle PUT requires both upload and publication permissions. Publication permission for `trusted-ci` is issued only to service accounts explicitly granted that namespace; personal credentials are read-only. P0 service-account credentials cannot call IAM/policy-management APIs; CI reporting separately checks `event.write`.

Each request proceeds in order: authenticate → confirm an active principal/member → resolve the tenant from trusted routing → validate the member's or credential's tenant → load resources in that tenant → intersect roles, grants, and token scopes → check action, trust domain, expiration, and status → execute. The server constructs `RequestContext` with principal, tenant, project, namespace, credential, and policy_version; client-supplied identity headers with these names are ignored or rejected.

List and single-record reads share a repository interface that requires `TenantScope`; there is no unscoped business `findUnique(id)`. Queries must take this form:

```text
WHERE tenant_id = authenticated_scope.tenant_id
  AND project_id IN authorized_projects
  AND (validated_client_filters)
```

Client `project_id`, search, `OR`, and export predicates always go in the final parentheses and cannot overwrite the first two conditions. An empty authorization set means no results. Nonexistent resources, other tenants, and invisible projects all return 404; a forbidden action on a visible resource returns 403. Updates and deletes include the same scope and `revision` in their SQL predicates; checking permissions first and then writing without scope is prohibited. The same applies to relational queries, aggregates, audits, and asynchronous workers. Platform operations APIs use a separate `/api/v1/platform` path and role; a single `isAdmin` cannot bypass every tenant restriction.

## 4. Human Sessions and Native-Tool Credentials

The management browser uses server-side sessions with `Secure,HttpOnly,SameSite=Lax` cookies; only a verifier for the session secret is stored. All mutations validate the CSRF token and Origin. P0 uses local password login, disables public registration, and defaults to 8-hour sessions. Roles are reevaluated on every management request; removing a member revokes authorization for that tenant, while disabling a user revokes all sessions. Production startup fails if a session secret, token pepper, or trusted TLS-termination configuration is missing; a trusted ingress may terminate TLS. P1 OIDC connects to the same User/Membership model without introducing another permission system.

Build tools use opaque keys in the format `exp_v1_<credential_uuid>_<random_secret>`, with at least 256 random bits. The database stores `HMAC-SHA-256(pepper,full_key)` and the pepper version; comparisons use a constant-time implementation. The pepper is managed as an installation secret, separately from database backups. Normal responses return only the key ID/prefix and metadata. Secrets must not be stored in logs, URLs, localStorage, downloaded configuration files, or audits.

| Entry point | Transport and mapping |
|---|---|
| Gradle HTTP | HTTP Basic over TLS, fixed username=`expbuild`, password=full key; maps to the same credential/principal |
| REAPI/gRPC | Metadata `authorization: Bearer <full_key>`; HTTP/2 proxies preserve the header; proxy-asserted tenants are not trusted |
| Management browser | Session cookie; cannot call cache endpoints, and build keys cannot impersonate browser sessions |
| Internal data plane | Separate node mTLS identity; may call only explicitly authorized policy, authentication, and event interfaces |

Native routes are fixed as follows; IDs in paths still require authorization checks:

```text
REAPI instance_name:
tenants/{tenant_id}/projects/{project_id}/namespaces/{namespace_id}

Gradle base URL:
/cache/gradle/v1/{tenant_id}/{project_id}/{namespace_id}/
```

The same key may use either credential transport, but can access only namespaces in its grants that match the protocol. An empty instance_name, missing tenant path, or unknown authentication method must not fall back to a default public cache. Native HTTP/gRPC returns each protocol's native statuses, not the management API JSON envelope described below.

## 5. Management API v1

All of the following are proposed contracts. The tenant root is `T=/api/v1/tenants/{tenant_id}`; `P=T/projects/{project_id}`; `N=P/namespaces/{namespace_id}`. Creation returns 201, reads/updates 200, deletion without a response body 204, and asynchronous operations 202. Each returned object includes `id,revision,created_at,updated_at`, with UTC RFC3339 timestamps; byte counts are decimal strings to avoid JavaScript precision loss.

| Method and path | Key request fields | Key response fields / authorization |
|---|---|---|
| `POST /api/v1/sessions`; `DELETE /api/v1/sessions/current`; `GET /api/v1/me` | Login email/password; logout CSRF | Cookie; user and summaries of joinable tenants, no token or complete project objects |
| `GET T`; `PATCH T` | name; `If-Match` | Tenant; only admin may modify |
| `GET/POST T/memberships`; `PATCH/DELETE T/memberships/{id}` | user_id/role; new users use a separate join invitation | Member metadata; admin; removal protects the last administrator |
| `POST T/invitations`; `POST /api/v1/invitations/accept` | email/role/expiry; one-time code and registration details | Invitation secret returned only once; cannot be replayed after expiration, use, or revocation |
| `GET/POST T/teams`; `PUT/DELETE T/teams/{id}/members/{user_id}` | name; member identity | Flat teams; admin |
| `GET/POST T/projects`; `GET/PATCH P` | name/description | Project; admin creates, maintainer modifies |
| `GET/PUT/DELETE P/bindings/{subject_type}/{subject_id}` | Fixed role | Project binding; admin/maintainer cannot grant beyond their own management scope |
| `GET/POST P/namespaces`; `GET/PATCH N` | name/protocol_id/trust_domain; PATCH only name/status | Namespace and client routes; maintainer |
| `GET/PUT N/policy` | quota, retention, limits; If-Match | revision, authz_epoch, application status; maintainer |
| `GET N/grants`; `GET/PUT/DELETE N/grants/{subject_type}/{subject_id}` | actions; subject_type is `principal/team` | Concrete namespace grant; accepts only valid principals or flat teams in the same tenant |
| `GET/POST P/service-accounts`; `PATCH P/service-accounts/{id}` | name/status | Principal ID, grant summary; maintainer |
| `GET/POST T/credentials`; `GET T/credentials/{id}` | principal_id/name/namespace_scopes/expires_at | Metadata; initial creation response also includes secret; permissions checked by principal and project |
| `POST T/credentials/{id}/revoke`; `POST .../{id}/rotate` | revoke reason; rotate overlap_seconds/expires_at | revoked_at/enforcement status; initial rotation response also includes new secret |
| `GET N/entries` | writer_token_id/writer_principal_id/time/cursor | Entry metadata, generation, provenance; `metadata.read` |
| `POST N/invalidation-previews`; `POST N/invalidations` | selector; preview_id | Preview operation; invalidation operation; `cache.invalidate` |
| `DELETE N`; `GET T/operations/{id}` | If-Match; no arbitrary resource URL | Operation; references cleaned asynchronously after namespace rejects new access |
| `GET T/audit-events`; `GET N/usage`; `GET N/onboarding` | Time, authorized scope, pagination | Audits, actual usage and freshness, native configuration templates without secrets |

P0 namespace policy fields: `storage_hard_bytes,object_hard_count,entry_hard_count,max_object_bytes,max_concurrent_uploads,request_rate_limit,download_soft_bytes,entry_ttl_seconds,unreferenced_blob_ttl_seconds,min_retention_seconds`. `object_hard_count` limits visible blobs; `entry_hard_count` independently limits cache entries. They map to the quota account's `blob_limit` and `entry_limit`, respectively. The data plane enforces them per protocol. Minimum retention constrains cleanup ordering; it does not guarantee continued write acceptance when space is exhausted. See the cache core for hard-quota enforcement. Reducing a quota below current usage plus reservations blocks only new positive-increment admissions and raises an alert; reserved uploads may settle without an increment, and data is not automatically deleted. Download budgets must be labeled soft.

Credential creation example; OpenAPI will pin the schema and enums during development:

```json
{
  "principal_id": "<service-account-uuid>",
  "name": "main-ci",
  "expires_at": "2026-12-01T00:00:00Z",
  "namespace_scopes": [
    {"namespace_id": "<uuid>", "actions": ["cache.read", "blob.write", "result.publish"]}
  ]
}
```

The secret field is returned only on the initial successful creation/rotation; all other responses omit it. Tokens must expire; P0 defaults to 30 days with an installation-wide maximum of 90 days. These are operational defaults awaiting pilot confirmation. Ordinary developers can issue only their own read-only credentials for authorized namespaces; maintainers can issue credentials only for service accounts in their project, not for other people.

## 6. Pagination, Concurrency, Idempotency, and Background Tasks

Lists default to `limit=50`, with a maximum of 200. Cursors are server-signed opaque values bound to the tenant, filter digest, and `(created_at,id)` sort position. Every page reauthorizes; a cursor cannot preserve revoked permissions. Whole-table totals are not computed by default. Metric responses include `observed_at,window,sample_count,status`; `no_samples/stale/unavailable` must not become 0.

PATCH/PUT/delete require `If-Match`: missing returns 428, revision mismatch 412. Creation and asynchronous mutations support `Idempotency-Key`; records are unique by `(tenant,actor,method,path,key)`. A retry with the same body digest returns the original resource/operation; a different body returns 409. Records are retained for at least 24 hours. Idempotency records and business changes commit in the same transaction, and the current caller's continuing permission is checked.

Sensitive changes such as roles, grants, and credential issuance lock the tenant's authorization version inside the transaction, revalidate the actor, then write the result and new epoch. A stale administrator check outside the transaction cannot authorize issuance. The last-administrator check uses the same tenant row lock so two concurrent removals cannot both conclude that “another administrator remains.”

**Exceptions to one-time secret display must be handled explicitly.** Credential-creation idempotency records do not retain the secret; repeated requests return only the created credential's metadata and `secret_available:false`, without regenerating that credential or replaying plaintext. If the first response is lost, the client revokes that credential using the returned ID, then creates another with a new idempotency key. The UI displays “The key cannot be recovered. Revoke and recreate it.” A lost rotation response similarly requires revoking the new key and recreating it, without deleting the old key early. During rotation, the old key remains valid until an explicit overlap deadline by default (default 1 hour, maximum 24 hours); the API returns both IDs and their expiration times. Once the new key is confirmed usable, the old key may be revoked immediately. Join invitations use the same revoke-and-recreate strategy when a secret is lost.

The error body is fixed as `error:{code,message,request_id,details?}`: 400 invalid input, 401 invalid authentication, 403 forbidden action, 404 invisible resource, 409 conflict, 412 version conflict, 429 rate limit with Retry-After, and 503 unavailable dependency. details contains only safe field errors, never SQL, tokens, external project names, or storage keys.

`Operation` fields are `id,tenant_id,kind,status,requested_by,progress,result,error,cancel_requested_at`; statuses are `queued/running/succeeded/failed/cancelled`. Tasks are durable and leased, support crash retries, and use the tenant scope fixed at submission. Before each batch of destructive writes, workers revalidate resource state and authorization; revoked permissions pause/fail the task, and worker identity cannot expand its scope. Cancellation stops only at batch boundaries; completed invalidations cannot be portrayed as rolled back.

Namespace deletion first marks it deleting and increments the authorization version, then asynchronously invalidates results and cleans references. The API shows the revocation propagation window and cannot promise every node has stopped when the request is accepted. P0 project deletion requires deletion of all namespaces to finish; there is no universal cross-tenant bulk-delete endpoint.

## 7. Policy Distribution, Disconnection, and Long-Stream Revocation

P0 uses “versioned snapshots + short-lived authorization leases”; database pepper/verifiers are not sent to the data plane. Node certificates and allowed tenants are provisioned at deployment; automatic enrollment is deferred. Nodes use mTLS for internal interfaces:

| Internal interface | Content and constraints |
|---|---|
| `POST /internal/v1/auth/introspect` | Raw key submitted once over TLS; control plane checks the database and current permissions and returns a signed AuthorizationLease; request logs must mask the credential |
| `POST /internal/v1/auth/renew` | mTLS node submits the original unexpired signed lease, active_stream_id, and current stream namespace/actions; control plane rechecks current principal, credential, membership/grants, and epoch, then returns a new signed lease no broader than the intersection of current permissions and the original lease scope; no raw key required |
| `GET /internal/v1/policies?after={sequence}` | Incremental or full snapshots with tenant epoch, signature, issued_at/expires_at; valid for at most 300 seconds; out-of-order delivery, gaps, or restarts trigger a full snapshot; HTTPS polling every 15 seconds, notifications only accelerate it |
| `POST /internal/v1/policy-acks` | node_id/tenant_id/epoch/applied_at, used to display propagation status; browsers cannot submit these |

A lease contains `lease_id,issuer,audience=node_id,principal_id,credential_id,tenant_id,namespace_scopes,authz_epoch,issued_at,expires_at`; it is valid for at most 300 seconds and never beyond key expiration. A node uses only `HMAC(node_local_key,full_key)` as its in-memory cache index and never caches plaintext; it verifies signature, audience, clock, and tenant route. Cache hits also require a valid snapshot and matching epoch. On first use or a cache miss, control-plane disconnection causes rejection; existing permission lasts only until the earliest lease/snapshot/key expiration.

`renew` only lets nodes continue still-active requests; it is not a general token-exchange interface. Nodes normally start renewal 30 seconds before the original lease expires and must receive and validate the new lease before the old authorization becomes invalid. The control plane checks the original signature, node-bound audience, original expiration, and active scope, then reauthorizes against current database state. The new lease adds `active_stream_id`, is valid only for that stream and the same request's final commit, and is not written back to the general authentication cache. It cannot establish new requests or broaden actions. Each renewal remains limited to 300 seconds; key revocation/expiration, membership removal, or namespace disabling causes rejection. Expired leases cannot be renewed. After node restart, stream completion, or establishment of a new RPC, the client must resubmit its key for introspection. Signed leases are restricted sensitive credentials and must not be written to logs or disk. This mechanism neither reconstructs a key from its HMAC index nor extends authorization offline merely because reads continue.

Authorization-affecting role/member/team/grant/key changes and namespace disabling commit in the same transaction as tenant `authz_epoch++`, audit, and outbox. On receiving a higher epoch, nodes immediately stop data access under old leases. New requests repeat introspection; active streams whose original lease has not expired may renew online and resume only after receiving authorization for the current epoch; otherwise they are interrupted. For simplicity, P0 may invalidate leases for the whole tenant; future versions may narrow this by principal. Snapshots contain namespace protocol, trust, status, current_policy_version, and resource limits; nodes construct context and record that policy version. Neither snapshot refreshes nor continued reads may extend old leases. Nodes load only configured allowed tenants; node identity does not grant a principal's artifact-access permissions.

The target from control-plane commit to revocation is ≤60 seconds under normal connectivity; existing authorization during disconnection lasts at most ≤300 seconds. These are design targets requiring acceptance testing. Active uploads/downloads are checked every 5 seconds for epoch and lease expiration; clock tolerance is included within the window and does not add another 300 seconds. Long streams are interrupted if online renewal does not complete before expiration. Resumption, new RPCs, and upload commits all reauthorize; GC read leases do not replace authorization leases. Management APIs return `revoked_at,target_online_deadline,hard_lease_deadline,acknowledged_nodes,total_nodes`, avoiding misreporting database revocation as network-wide enforcement. P0 does not use direct object-storage upload URLs, so active streams can be terminated.

## 8. Write Provenance and Credential-Leak Response

Every published entry generation records `writer_principal_id,writer_token_id,policy_version,trust_domain,created_at,invocation_id?`. After credential revocation, a nonsecret tombstone remains for traceability; provenance is not cascade-deleted. User-supplied commits, invocations, and branches are correlation evidence only, not substitutes for the verified publishing principal; the UI clearly labels unverified information. CAS uploads separately record the uploading principal/credential and visibility authorization; the blob's original uploader must not be treated as the publisher of every result referencing it.

Revoking a key stops future access only; it neither automatically proves its historical artifacts untrustworthy nor deletes historical results. Response workflow: search by `writer_token_id` → generate preview → explicitly execute invalidation → warm again through trusted CI. Preview tasks freeze authorized `(namespace_id,key,generation)` candidates, retain counts, logical bytes, and a selector digest, and expire after 15 minutes by default. Execution invalidates only entries still matching that generation; versions created after the preview are not mistakenly deleted. Revoke the leaked key before previewing; scan again after the propagation window to catch missed writes.

Invalidation removes result visibility/root references and leaves physical blobs to reference-safe GC. A suspect result's provenance must not cause direct deletion of CAS content still referenced by trusted results. Record the actor, reason, candidate count, success/skip/failure counts, and associated credential ID. P0 provides API/CLI access and a minimal status page; P1 adds a more complete interface for complex response workflows.

## 9. P0 Acceptance and Open Questions

- Different projects within one tenant, different tenants, and forged routes/filters/cursors/related IDs must all fail to bypass authorization; explicitly cover the legacy pipeline filter-override case.
- Personal keys cannot publish to trusted-ci; CAS upload permission cannot update AC; project maintainers cannot issue keys for other projects or other people.
- Successful creation with a lost response, idempotency-key conflicts, lost rotation responses, retries after revocation, membership removal, and team unbinding all have deterministic states; responses and logs contain no historical secrets.
- Control-plane disconnection, out-of-order/missing snapshots, node restart, large-file streams lasting over 5 minutes, resumption, and commit all meet revocation boundaries. Expired leases, wrong nodes, and wrong active_stream_id values cannot renew; renewal cannot expand scope or create new requests; offline operation does not allow anonymous access.
- If entries are concurrently overwritten after a token-based preview, execution cannot invalidate the new generation. Asynchronous retries neither bypass authorization nor release quota twice; audit and mutation cannot have different commit outcomes.

The specific additional decisions are UUID routing, first-use key introspection, tenant epochs, recovery from lost secret responses, and explicit namespace grants. Compared with the main architecture's “deduplication within the same tenant/trust domain by default,” this phase narrows the scope to **deduplication within a namespace**. This tradeoff must be reflected in the master plan so P0 does not initially take on the complexity of cross-namespace authorized references and physical sharing. M0 must validate introspection throughput/disconnection experience, 15-second polling and the 60-second revocation target, default key lifetimes, and whether team management meets pilot needs. Changing namespace trust domains, cross-namespace sharing, and machine credentials for management automation are not default P0 capabilities.
